# 응답 전 필수 확인 게이트 — SPT 번역 애드온

**대상:** 이 프로젝트에 관한 모든 응답(조사, 설명, 아이템 목록, 번역/수정, 오류 분석, 빌드, 배포, 진행 보고, 후속 질문 포함). **문서를 한번 읽었다는 기억으로 재확인을 생략하지 않는다.** 이 문서는 `docs/AGENTS.md`와 `모드번역_작업절차.md` 0-A절에서 호출한다.

## A. 매 응답마다 먼저 수행 (PRE-RESPONSE)

1. **최신 기준 확인:** 사용자가 마지막으로 제공한 누적 소스 ZIP/현재 작업 디렉터리·원본 모드 버전·최신 인계 문서를 확인한다. 다른 턴의 복사본/과거 ZIP을 무심코 채택하지 않는다. 실제 파일 접근에 실패하면 그 사실부터 고지한다.
2. **절차 확인:** `docs/AGENTS.md`에 정의된 필수 열람 순서대로 본 문서와 `모드번역_작업절차.md` 0·0-A절을 실제로 다시 읽는다. 빠른 사실 질문에서도 생략하지 않는다.
3. **해당 규격 읽기:** 추가 문서 목록은 `docs/AGENTS.md`의 작업 종류별 표를 따른다. 빌드/배포는 실제 빌드 스크립트와 `docs/DISTRIBUTION_LAYOUT.txt`, 로딩/미번역은 `src/ClientLocaleModOverlay.cs` 및 관련 로더·원본 모드·최신 프로필·게임 증거를 확인한다.
4. **파일→근거 대조:** 답변에 나오는 아이템·원문·번역·모드·키·수량·완료 단계와 원본 경로를 실제 파일에서 확인한다. 사용자 메시지의 직접 관찰은 우선 증거로 삼되, 관찰로 입증되지 않은 내부 원인은 추정으로 구분한다.
5. **응답 직전 재검토:** 다음 B~D 게이트를 통과했는지 확인한다. 통과하지 않은 부분을 완료로 보고하지 않는다. 읽은 파일명·미검증 항목을 간단히 명시할 수 있지만, 읽지 않고 읽었다고 주장하지 않는다.

### A-1. 새 번역·업데이트의 버전 기록 확인

번역 또는 F12 작업을 마무리할 때 `docs/모드번역_작업절차.md` 2-B·5절에 따라 **변경 대상 전체 프로필**의 모드 버전·원본 자료·증거 유형을 확인한다. `mod_version`과 버전 관리 대장·근거 CSV의 일치/불일치/미확인 건수를 기록한다. 원본 근거가 없을 때는 추측하거나 공식 사이트 최신 버전을 실제 번역 검증 버전으로 간주하지 않는다. 이 확인이 누락되면 **버전 기록·문서 완료를 주장하지 않는다**.

## B. 번역이 영어로 남는 모든 화면의 공통 조사 게이트

아래 1~6은 아이템 예시이며 **상인 정보·퀘스트·자막·F12·독립 UI·메일에도 동일 원칙**을 적용한다. 해당 타입의 실제 데이터 공급 함수·후처리·적용 훅을 반드시 추적한다. 화면 한 곳의 오류는 **조사 출발점이지 수정 범위의 제한이 아니다.**

| 순서 | 확인 사항 | 증거가 없으면 |
|---|---|---|
| 1 | **게임 화면의 실제 이름/설명/단축명**을 각각 별도 문자열로 기록. 어떤 필드가 번역되고 어떤 필드가 영어인지 분리 | 스크린샷·로그 증거 필요로 표시 |
| 2 | 게임에서 표시된 아이템 **template/key** 및 서버가 전달한 `locale`의 **실제 영어 값**을 확인. 원본 ZIP의 언어파일은 참고이며 런타임의 대체 증거가 아님 | 실제 키·원문 `미확인` |
| 3 | 번역 JSON의 해당 `key`, `source`, `translation`, `display_type`, **상속되는 `match_mode`**를 확인 | 적용 가능 `미확인` |
| 4 | 로더의 정확한 후보 선택·원문 일치 조건·프로필 로드 순서·`mod_id`/동일 키 중복·부모 번역 보호를 대조 | 특정 원인 확정 금지 |
| 5 | 이름/설명/단축명 **전부** 같은 문제에 영향받는지 확인. 같은 원문 비교 규칙을 쓰는 **현행 지원 프로필 전체의 동일 로더·매칭 분기 관련 항목과 충돌 후보**를 조사 | 다른 항목은 `재감사 필요` |
| 6 | 수정 후 JSON 스키마·원본 대조·실제 런타임 원문 사례 테스트·빌드·배포 포함·인게임 재확인을 분리 기록 | 실제 적용 `미확인` |

**재발 사례:** 모드 원본 또는 번역 JSON에는 `VSK ...`인데 게임은 `VKS ...`라고 표시할 수 있다. 프로필 source가 로더의 exact 비교에 걸리면 이름과 설명이 모두 영어로 남을 수 있다. **이 사례에서 원본 ZIP과 JSON만 같다는 정적 검사는 불충분**하다. 또한 한 아이템의 텍스트 차이를 근거로 **프로젝트 전 항목이 같은 원인이라고 단정하는 것도 금지**한다.

게임에서는 단축명 `VSSK`처럼 **원문 유지가 정상인 경우**도 있으므로, 이름/설명의 미적용과 구별한다. 게임 텍스트 예시가 원본에 없는 새로운 별칭이라면, 원본/실제 로케일 값이 입증되기 전 자동 문자열 유사도 매칭·전역치환으로 해결하지 않는다.

**확인된 원문 변경을 수정하는 경우:** 사용자가 제공한 실제 화면이 `source`와 다르면 원문 출처를 별도 기록한다. `source_variants`를 사용하는 경우 키가 동일한지 확인하고, 허용된 변형만 원문 일치 검사에 포함한다. 설명·이름의 표시 병기, 원문 불일치 시 보존, 다른 프로필 우선순위, 실제 컴파일과 화면 재검증을 구분한다. **프로젝트 전체의 추가·수정 후보가 모두 적용됐다는 판정은 실제 게임 로케일 자료 없이는 금지한다.**

### 실게임 원문 스냅샷이 확보된 경우

실제 서버 로케일 스냅샷이 제공되면 **기존 프로젝트의** `docs/tools/audit_runtime_coverage.py`를 사용해
번역 프로필 `source`와 현장 원문을 전수 비교한다. 스냅샷이 없으면 이 검사를 실행한 척하지 않고
`실게임 원문 전수 대조 미실시`라고 기록한다.

```text
python docs/tools/audit_runtime_coverage.py --raw <게임_적용전_한국어_로케일.json> --english <게임_영어_로케일.json> --parent-english <부모_영어_로케일.json> --report <검증_보고서.json>
```

이 도구의 결과는 **검토 후보 목록**이다. 키 미존재, 다른 한국어 번역 보존, 원문 차이, 장식 문자열,
아이템 모델명 등을 사람이 실제 로더 규칙과 비교해 판정해야 한다. 도구의 `unmatched=0`이
곧 모든 아이템 인게임 번역 성공을 뜻하지 않는다. 필요한 파일의 출처·시점·게임 버전을 함께 남긴다.

**16차 재발 방지:** `translation`에 수동 `\n(영문 이름)`을 넣고 자동 한영병기에서 중복 출력된 사례를 전수 검사한다. 후보가 `translated`라도 `source == translation`이면 `source_kept`로 상태를 바로잡는다. 특히 원본 ZIP과 프로필 source가 모두 같다는 검사만으로 인게임 원문을 확인했다고 주장할 수 없다.

### B-1. 공급원·매칭 일치의 필수 확인

- 실제 모드에서 `원본 영어 JSON → 서버/클라이언트 등록 → transformer/최종화/덮어쓰기 → 부모·다른 모드 병합 → 로더 선택 → 출력` 순서를 조사한다. 같은 키에 복수 영어를 공급하는 함수가 있는지 확인한다.
- `키/공급원/언어별 조건/적용 순서/정적 예상 최종 영어/실제 서버 또는 화면 영어/프로필 source/상속 match_mode/첫 선택 후보/후크 연결`을 구분해 기록한다. `원본 JSON == 프로필 source` 검사만으로 정상이라고 판정하지 않는다.
- 사용자 화면·로그와 정적 추론이 모순되면 인게임 증거에 맞춰 실패 판정을 유지하고, 복수 공급원부터 재추적한다. 게임에서 확보하지 못한 최종 로케일 값은 `미확인`으로 남긴다.

## C. 완료 상태와 보고 언어

다음 상태는 **서로 독립**이며 다음 단계가 입증되지 않았다면 올리지 않는다.

1. `원본 후보 조사`
2. `번역 데이터 작성`
3. `JSON/정적 검사 통과`
4. `로더 연결/매칭 경로 확인`
5. `C# 실제 빌드 통과`
6. `dist/배포 ZIP에 반영 확인`
7. `인게임 번역 실제 표시 확인`

- `번역 작성 완료`는 2단계 완료를 뜻할 뿐 7단계 보장이 아니다. '번역된 아이템' 목록에서는 **번역 데이터 항목**과 **인게임 적용 확인 항목**을 나눠 표시한다.
- 실행 중인 애드온 로그의 버전 문자열만으로 현재 코드/설치 내용 전부를 확정하지 않는다. 동일 버전 개발 빌드가 존재할 수 있다.
- 스크린샷에서 번역이 실패하면 7단계 실패가 확정된 것이다. **실패한 동일 키의 7단계 완료 판정은 즉시 취소**, 관련 그룹은 재감사로 전환한다.
- 원인 미확정 상태에서는 원인 후보별 사실/가설을 분리하며, 사용자 설치/빌드 문제로 책임을 돌리지 않는다.
- 번역·소스·인계 문서 변경 후 상위 절차 7절의 후처리를 완료한다. 빌드나 인게임 확인을 실제 수행하지 않았다면 `미실시`라고 명시한다.

## D. 증거 충돌과 재감사 게이트

- 사용자 제공 인게임 증거가 과거 정적 검사에 반하면 **인게임 증거를 우선**하고, 그 정적 검사가 보장하지 못한 범위를 고지한다.
- 단일 결함을 고쳐도 같은 로더 경로/원문 검사에 의존하는 다른 신규·수정 항목은 `미검증`으로 둔다. **프로젝트 전체의 재감사 결과 없이 '모두 해결'이라 하지 않는다.**
- **영향 범위 산정 순서:** (1) 오류를 유발한 매칭 분기·후처리·훅 식별 → (2) 같은 분기를 사용하는 전체 번역 프로필·F12·서버 채널 검색 → (3) 현행 원본이 있는 항목은 원문·실제 공급 경로 대조, 없는 항목은 정적 영향과 `원본 미제공` 표시 → (4) 확인된 원인만 최소 수정 → (5) 확인한 전체 범위를 다시 검사한다. 발견 위치 하나만 고쳐 완료 처리하지 않는다.
- **현행 범위 회귀:** 기존 한국어·현재 버전 원문·표시 유형은 보존한다. 사용자가 지원 종료를 지시한 구버전 전용 영어와 호환 프로필·스크립트는 복구 대상이 아니다. 동일 최신 버전의 복수 원문은 구버전 호환으로 오인하지 않는다.
- **덮어쓰기 재현:** 빈 설치와 기존 설치에 같은 배포물을 적용해 파일·로드 대상·중복·잔존 구형 프로필을 비교한다. 불필요한 삭제를 임의로 안내하지 않으며 필요 시 승인된 예외만 반영한다.
- 중복 로케일 키는 값·원문·로드 순서를 보고 분류한다. 중복 키 수만으로 충돌이 전부 실패했다고 결론짓거나 임의 삭제하지 않는다.
- 재감사 인계에는 `발견 증거`, `영향 받을 범위`, `확정 원인`, `수정 내용`, `각 단계별 검증`, `남은 미확인`을 필수 기록한다.
- 검증 환경이 부족하면 도구 제약을 명시하고, 확인 가능한 범위에서만 진행한다. 불명확함을 통과 판정으로 채우지 않는다.
