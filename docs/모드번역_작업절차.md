# SPT 모드 번역 작업 절차 — 분석·구현·검증·전달

이 문서는 **작업 절차의 최상위 기준**이다. 사용자가 제공한 `SPT-Korean-Mod-Translation-Addon`과 번역할 원본 모드를 다루는 GPT가, **이전 턴의 분석 결과를 다음 턴의 구현과 최종 산출물에 연결**하기 위해 따른다. 구체적인 번역 문체·용어는 `prompts/translate_prompt.txt`, 스키마 및 표시 종류는 `TRANSLATION_FORMAT.md`, 실제 구현은 제공된 **최신 애드온 소스**가 기준이다. 문서와 실제 소스가 서로 다르면 차이를 밝혀 확인하고, 소스의 현재 동작이 사용자 지시를 무효화한다고 해석하지 않는다.

## 0-A. 매 답변 전 문서 재확인 (필수 · 모든 턴)

문서 열람 순서와 작업별 필수 문서는 `docs/AGENTS.md`에서만 정의합니다. 수행 전 해당 지침을 다시 읽고, **답변 전 증거·실패 판정**은 [`응답전_필수확인.md`](응답전_필수확인.md)를 따릅니다. 문서 접근이 불가능하거나 게임 적용 증거가 없으면 완료로 보고하지 않습니다. `python docs/tools/verify_workflow.py documents`는 문서 구조 검사이며 실제 열람이나 게임 적용의 증명은 아닙니다.

## 0. 모든 단계에 적용하는 원칙

1. **요청 범위를 정확히 유지한다.** 사용자가 분석만 요청하면 번역·코드를 만들지 않는다. 번역을 요청하면 해당 모드와 확정 범위 안에서 처리한다. 제외한 모드·기능은 건드리지 않는다.
2. **사용자가 확정한 규칙을 우선한다.** `BEAR`, `USEC`, `RUAF`, `UNTAR`는 영문 유지. 번역 어휘·화자·병기·치환변수·원문 보존은 Prompt와 스키마를 적용한다. 현재 소스는 *어떻게 적용되는지*의 근거다.
3. **기존 프로젝트 규격 안에서 구현한다.** `translations`, `config-ui`, 기존 연결된 `native-locales` 및 지정된 C# 클라이언트/서버 훅을 확인한다. JSON만으로 불가능하면 **애드온 내부의 정확한 적용 지점**을 최소 확장한다. 모드 원본 파일·DLL·서버 웹 소스를 임의로 수정하거나, `extras`·별도 설치 패치·새 로더/범용 엔진을 만들어 우회하지 않는다. 애드온 내부에서 구현 불가능하다고 판단되면 근거와 미완료 범위를 보고하고 사용자 결정 없이 다른 구조를 채택하지 않는다.
4. **파일 작성과 실제 적용은 다르다.** JSON, 훅 소스, 컴파일된 DLL, 배포 ZIP, 게임 내 표시를 각각 다른 상태로 기록한다. 검증되지 않은 단계를 완료로 보고하지 않는다.
5. **이전 턴의 조사를 잇는다.** `번역대상_인계기록_양식.md` 형식으로 확인된 후보와 적용 경로를 `docs/records/work-history/`에 남긴다. 다음 턴은 이 기록과 새로 받은 원본을 먼저 대조한다. 기록이 없거나 버전이 바뀌면 해당 부분을 재조사한다. 과거 분석이 있었다는 말만 믿고 검증을 생략하지 않는다.
6. **추정과 사실을 분리한다.** 문자열 상수의 존재 ≠ 사용자에게 표시됨, 기존 JSON 존재 ≠ 연결됨, 소스 훅 존재 ≠ 빌드됨, 빌드됨 ≠ 게임에서 표시됨. 확실하지 않으면 `미확인` 또는 `보류`로 기록한다.

## 1. 첫 번째 요청 — 애드온 소스와 Prompt 분석

번역할 새 모드를 보기 전에 현재 제공된 애드온을 확인한다.

- **현재 기준 확보:** ZIP의 프로젝트 버전·폴더 구조·클라이언트/서버 프로젝트·빌드 스크립트·현행 `translations`, `config-ui`·기존 전용 훅/어댑터를 확인한다. 과거 배포본·임시 분석본으로 최신 작업물을 덮어쓰지 않는다.
- **문서 읽기:** `docs/AGENTS.md`의 작업 종류별 필수 목록에 따라 `번역작업안내서.md`, `TRANSLATION_FORMAT.md`, 번역 시 `prompts/translate_prompt.txt`를 확인한다. 부모 패턴 감사와 과거 기술 문서는 필요한 내용에 한해 참고하며 현행 소스를 우선한다.
- **적용 경로 표 작성:** 글로벌 `locale`, `locale_additions`/fallback/clone, F12 일반 설정과 CustomDrawer, 지정 `small_ui`·알림·팝업, 서버 메일/오류, 자체 로케일 로더 및 기존 전용 훅의 **프로필 ID·채널·타입/메서드·로드 위치**를 분류한다.
- **제한 이해:** F12 값/내부 enum, 로그/키/파일명/게임 로직을 번역하지 않는다. 훅은 전역 UI 치환이 아니라 확인된 메서드·호출자에 제한한다. `reference_only` 및 파일만 존재하는 채널은 실제 적용 경로가 아니다.

**완료 산출:** 새 모드 분석에 재사용할 수 있는 **애드온 기능·적용 경로·제약 요약**. 이 단계에서는 사용자가 요구하지 않는 한 번역·소스를 수정하지 않는다.

## 2. 두 번째 요청 — 새 모드의 전체 사용자 표시 대상 조사

새로 제공된 **원본 모드의 실제 버전**과 이전 조사 대상을 비교하고, 모드별로 다음을 조사한다.

- **로케일:** 아이템/의류의 이름·단축명·설명, 퀘스트의 제목·설명·목표·메시지, 상인·업적·읽는 문서·지도 라벨·직접 메일·서버 오류·다국어 리소스.
- **F12:** 플러그인 GUID, `section`·`key`별 표시명·설명·분류, 선택지의 화면 표시, 조건부 설정, 숨김 처리된 값과 사용자 지정 `CustomDrawer` 구분. 설정의 저장 값이나 enum 내부 이름은 수정 대상이 아니다.
- **독립 UI:** TMP/Text, IMGUI/GUILayout, 버튼·툴팁·알림·팝업·사망 화면·편집기, 동적으로 연결/캐시되는 문자열과 언어 변경시 갱신 경로.
- **서버·웹:** 직접 메일·시스템 메시지, 서버가 생성하는 표시 문자열, Razor/JavaScript 등 클라이언트 훅으로 처리되지 않는 웹 UI. 실제 웹 화면이라고 확인한 경우에도 원본 서버 코드를 패치하는 방법을 자동 승인하지 않는다.
- **DLL만 있는 경우:** 확인 가능한 문자열과 호출 경로, 확인 불가능한 출력 위치를 구분한다. 이름만 비슷한 다른 플러그인이나 관련 모드는 **별도 GUID/모드**로 판별한다.

각 후보마다 **원본 버전/경로 → 키 또는 어셈블리·타입·메서드 → 실제 표시 위치 → 기존 번역 유무 → 적용 채널·훅 → 필요 작업 → 검증 상태**를 남긴다. 단순 로그·내부 식별자·숨겨진 설정 등은 `비대상`으로 분류하고 이유를 적는다. 기존의 번역 데이터도 새 원문·버전과 대조해 적용 불일치를 찾는다.

### 2-A. 실제 문자열 공급·후처리 경로 조사 게이트 (번역 시작 전 필수)

1. **공급원 전수 추출:** 원본의 언어 JSON만이 아니라 등록/생성 C#·DLL 상수, 서버 transformer, 동적 퀘스트·아이템, UI 텍스트 대입을 검색한다. 로그·내부 ID·숨김 설정과 실제 사용자 표시 후보를 분류한다.
2. **동일 키의 복수 공급원 찾기:** `로케일 키/모드 버전/원본 파일·메서드/입력 영어/호출 조건/언어`로 묶는다. 같은 키의 `en.json`과 서버 `AddTraderToLocales`처럼 값이 다르면 **어느 쪽도 자동으로 최종 원문으로 확정하지 않는다.**
3. **등록→후처리→로더 순서 확인:** 초기 값, 다른 모드·부모 병합, 조건부 덮어쓰기/기존 값 보존, 언어별 분기, 캐시·클라이언트 전달을 추적한다. 코드로 예상한 최종 영어와 **실제 게임/서버 스냅샷에서 관찰한 영어**는 서로 다른 증거 등급으로 기록한다.
4. **정확한 적용 판정:** 그 문자열과 번역 `source`·허용된 후보·상속 `match_mode`·프로필 선택 순서·연결된 훅을 비교한다. 경로가 불명확한 항목은 `미확인/보류`이며, JSON 등록만으로 `적용 완료`가 아니다.
5. **작업 차단:** 현행 모드의 표시 후보 목록과 경로·미확인 범위를 정리하지 않은 채 일괄 원문 교체나 `완역/전체 적용` 판정을 하지 않는다. 원본 모드·DLL 자체를 번역 목적으로 수정하지 않는다. 상세 표와 재현 입력은 `번역작업안내서.md` 2-3절 및 `번역대상_인계기록_양식.md` B-1절을 따른다.

### 2-B. 원본 모드 버전 확인 및 기록 게이트 (신규·업데이트·F12 작업 필수)

1. **대상 식별:** 작업하는 `translations/*.json`과 `config-ui/*.json`을 `mod_id`·플러그인 GUID로 찾아 원본 모드에 연결한다. 동일 모드의 일반 번역과 F12가 서로 다른 소스를 기준으로 작성되었을 수 있으므로 프로필 **각각** 확인한다.
2. **원본 버전 확인:** 사용자 제공 ZIP·메타데이터·메인 프로젝트·실제 모드 릴리스 정보를 대조한다. 파일명과 내부 버전이 다르면 하위 라이브러리/어셈블리 기본 버전인지 조사하고 근거를 남긴다. `target_spt` 및 `4.1-dev` 같은 SPT 호환 브랜치를 모드 릴리스 버전으로 대체하지 않는다. **숫자가 더 높다는 이유만으로 다른 종류의 버전을 채택하지 않는다.**
3. **근거 등급 분리:** `확보 원본 버전`·`공식 사이트 조회 버전`·`실제 원문/코드 검증 버전`·`과거 최초 번역 기준(입증된 경우)`을 구별한다. 사이트에 표시된 최신 릴리스만 확인했으면 그 상태와 조회일·URL을 남기고, 보관 소스나 인게임의 검증 버전이라고 주장하지 않는다.
4. **프로필 기록:** 작업 대상으로 확인된 실제 모드 릴리스 버전은 해당 JSON 최상위 `mod_version`(문자열)에 기입하거나 갱신한다. F12도 별도 기입한다. 근거가 부족하면 **기존 값이 검증된 것처럼 갱신하거나 추측으로 기입하지 않으며**, 필드 미기록 사유와 작업 상태를 기록한다.
5. **관리 대장 동기화:** `docs/records/versioning/번역_원본모드_버전관리대장_20261023.md`와 `docs/records/versioning/번역_원본모드_버전_근거목록_20261023.csv`에 프로필 경로, 버전, 소스 ZIP/릴리스 URL, 확인일, 버전 근거의 종류, 번역 적용 검증 상태를 기록한다. 기존 버전값을 바꿨으면 이전 값과 변경 이유도 작업별 인계 기록에 남긴다. 근거 CSV의 열 구조는 불필요하게 변경하지 않고 기존 `basis`·`evidence_type`·`checked_on` 등으로 구분한다.
6. **누락 처리:** 버전 확인을 시도했으나 확정할 수 없다면 대장·인계 기록에 `미확인`과 실제 조사한 소스, 부족한 증거를 명시한다. 해당 프로필을 **버전 확인 완료 또는 해당 버전 번역 검증 완료로 판정하지 않는다**. 사용자 요청 범위의 나머지 분석·번역까지 무조건 중단하지는 않되, 최종 보고의 미완료 항목에 포함한다. 지원 종료한 구버전 전용 원문/호환 프로필을 복구하지 않는다.

**완료 산출:** 사용자에게 번역을 시작하기 전에 알려줄 대상 규모, JSON만으로 해결되는 범위, 코드 확장이 필요한 범위, **미확인/지원 불가 경로와 모드별 버전·근거 상태**. 자세한 후보표와 버전 확인 결과는 인계 기록으로 유지한다.

## 3. 작업량·시간초과 위험을 판단해 분할 여부 결정

분할은 의무가 아니다. **모드 수가 아니라 실제 문자열 수·설명 길이·훅의 복잡도·테스트/패키징 부담**을 보고 판단한다.

- 작은 F12/로케일 작업 여러 개라도 한 번의 실행에서 검증과 저장까지 안전하게 끝낼 수 있으면 묶어서 진행한다.
- 수백 개의 항목, 긴 대사, 여러 출력 경로, 새로운 클라이언트/서버 훅 등으로 장시간 작업과 취소 위험이 있으면 **독립 검증·저장이 가능한 회차**로 나눈다. 30분 가까이 걸릴 것으로 보이면 더 작게 쪼갠다.
- 아이템의 Name/ShortName/Description, 하나의 화면에서 맞물리는 문구, 같은 훅의 규칙 등은 가능한 같은 회차에 묶는다. 회차 수를 먼저 정하고 항목을 기계적으로 균등 분할하지 않는다.
- 각 회차에 **고정 범위(키·모드·버전), 선행 결과물, 검증 기준, 예상 산출물, 다음 회차의 남은 항목**을 정한다.
- 처리 중에는 회차별 실제 파일을 저장하고, 인계 기록의 `완료/보류/미완료`를 갱신한다. 다음 턴에서 키·훅 중복을 피하기 위해 **마지막 누적 파일과 현재 원본**을 다시 확인한다.

## 4. 번역·구현 실행

1. `prompts/translate_prompt.txt`와 `TRANSLATION_FORMAT.md`를 **실제 번역 시작 전에 다시 확인**한다. 기존 확정 용어·화자 말투·세력명·영문 이름/모드명 자동 표시 규칙을 따른다.
2. **원본 모드의** 키/ID·영어 문자열·태그·변수·저장값·로직 식별자는 수정하지 않는다. 번역 프로필의 `source`는 현행 모드에서 **해당 키의 실제 공급·선택 경로가 확인된 경우에만** 필요에 따라 갱신한다. 증거 없이 `en.json`에 맞춰 일괄 변경하거나 이미 유효한 현재 원문을 삭제하지 않는다. `source_variants`의 제한 조건은 `TRANSLATION_FORMAT.md`를 따른다. **`translation`에는 번역 본문만** 넣는다.
3. 기존 프로필과 정확한 GUID/`mod_id`/채널을 재사용한다. 새 채널/파일명을 임의로 만들지 않는다. 다른 모드의 번역을 실수로 덮어쓰지 않는다.
4. 데이터만으로 적용되는 경로는 JSON만 수정한다. 연결이 없다면 원본 모드의 실제 출력 지점을 찾아 **애드온 내부의 기존 훅을 최소 확장**한다. F12 CustomDrawer, 서버 전송, 독립 GUI, 자체 로케일, 웹 UI를 일반 F12 또는 일반 `locale`로 뭉뚱그리지 않는다.
5. 훅 확장 시 의도하지 않은 호출자나 게임 로직을 바꾸지 않게 범위를 제한한다. 원문 불일치·대상 부재·영어 모드에서는 원래 동작을 보존하며 언어 전환과 캐시 갱신을 확인한다.
6. 독립 적용 경로를 구현하지 못했다면 `미완료`로 남긴다. **별도 패치 파일 생성이나 원본 모드 수정으로 대체하지 않는다.**
7. 번역·F12 항목을 신설하거나 업데이트했다면 작업 중 확보한 모드 버전 근거를 2-B절에 따라 대상 JSON과 버전 관리 대장·근거 CSV에 **같은 작업 회차에서 반영**한다. 이 버전 기록은 번역 품질/적용 확인과 별개이며, `mod_version`의 변경만으로 실제 원문 일치나 호환성이 검증된 것으로 보고하지 않는다.

## 5. 회차마다 반드시 수행할 역방향 검증

- **원본 → 결과물:** 2단계에서 찾은 후보 **모두**가 번역/원문유지/비대상/보류 중 하나로 분류됐는지 확인한다. 원본 파일의 신규 로케일 키·F12 설정·독립 UI를 다시 훑어 **목록에조차 없던 누락**을 찾는다.
- **결과물 → 실행 연결:** 각 번역 행·채널이 실제 애드온 로더/프로필/훅에 연결되는지 확인한다. JSON만 등록한 미연결 UI 문자열을 완료로 세지 않는다.
- **현행 지원 범위 회귀:** 기존 정상 번역의 키·원문·한국어·표시 유형·훅을 모드별로 대조하고 실제 로더 후보 선택도 확인한다. 최신 지원 버전에서 여전히 사용되는 값은 보존한다. **지원 종료된 구버전 전용 영어는 100% 보존의 대상이 아니며**, 호환용 프로필·스크립트는 다시 만들지 않는다. 동일 최신 버전에 복수 공급원이 있다면 코드·실행 증거로 현재 값임을 따로 확인한다.
- **공통 원인 영향 검사:** 오류가 하나라도 확인되면 같은 `match_mode`/훅/로더 분기를 사용하는 **지원 프로필 전체**를 검색해 정상·실패·미확인을 기록한다. 수정은 근거가 확인된 경로로 제한하고, 수정 후 해당 전체 범위의 회귀를 다시 실행한다. 구버전 전용 불일치, 현재 버전의 오류, 원본 미제공으로 인한 미확인을 섞지 않는다.
- **설치 방식 회귀:** 빈 모의 설치와 기존 설치에 대한 덮어쓰기를 각각 구성해 최종 파일·로딩 대상·잔존 구형 파일을 비교한다. 덮어쓰기만으로 삭제되지 않는 충돌 파일은 별도로 기록하고 설치 문구 변경 시 승인 규칙을 따른다.
- **버전 기록 역검증(필수):** 새로 작성·갱신한 일반 번역/F12 **모든 대상 프로필**의 `mod_version`과 `docs/records/versioning/번역_원본모드_버전관리대장_20261023.md`·근거 CSV의 값을 1:1 대조한다. `대상 N / 기록·근거 일치 N / 미확인 N / 불일치 N`을 기록하고, 버전·원본 파일/URL·근거 등급·확인일 누락을 점검한다. `build/build_supported_mods.py`를 실행해 공개 지원 목록의 일반 번역·F12 버전 표기가 JSON과 일치하는지 확인한다. 미확인 건을 임의 버전으로 채우거나 검증 완료로 표시하지 않는다. 웹 최신 버전만 등록된 경우 실제 번역 근거 버전으로 오인하지 않는다. **불일치가 남은 경우 문서/버전 기록 완료 판정 금지.**
- **기존 데이터 보존:** 동일 모드 기존 행, 다른 모드 프로필, 사용자 확정 번역을 비교한다. 중복 키·GUID·`mod_id`, `source` 원문 불일치, 치환 변수/리치텍스트, F12 선택값을 검사한다.
- **검증 단계 표시:** JSON 스키마/정적 검사 → 실제 공급 경로·로더 후보 시험 → C# 빌드 → 배포 ZIP 포함 및 덮어쓰기 검사 → 실제 게임 표시 확인을 **별도 결과**로 기록한다. 검사마다 `전체 대상 N건 / 확인 N건 / 실패 N건 / 미확인 N건`과 증거 위치를 남긴다. 하나의 통과 결과로 다음 단계를 추정하지 않는다.
- **변경 후 회귀 확인:** 훅/로더를 수정했으면 다른 언어에서 원문 유지, 언어 전환, 모드가 없을 때 안전한 동작, 다른 모드 화면 침범 여부를 검토한다.
- **실패 시 대응:** 정확한 오류와 해당 파일을 확인·수정한 뒤 재검증한다. 실패한 상태를 `통과`, `100% 적용`, `완료`로 표시하지 않는다.

## 6. 결과물 요청의 뜻을 구별한다

| 사용자 요청 | 제공할 것 | 기본적으로 포함하지 않을 것 |
|---|---|---|
| `소스파일`, `번역된 소스`, `다음에 빌드할 소스` | 기존 프로젝트 구조를 유지한 **전체 수정 소스**(필요한 코드·설정·실제 번역 데이터·기존 프로젝트 파일 포함) | 개발 중간 메시지, 임시 분석 로그, 불필요한 작업 회차 산출물, 독립 `extras` 패치 |
| `업로드용`, `배포용`, `설치용 빌드` | 실제 빌드된 사용자 설치용 ZIP. 확인된 배포 구조(`BepInEx`, `SPT_Runtime`)와 필요한 런타임·번역 데이터만 | 프로젝트 소스, 테스트, 개발 보고서, 중간 노트, `extras`, 임시 파일 |
| `번역 JSON 패치` | 사용자가 명시한 JSON만, 적용 범위와 필요한 기존 훅 연결 설명 | 컴파일되지 않은 기능을 설치 가능한 것처럼 주장하는 안내 |
| `조사`, `누락 목록`, `계획` | 분석 결과·분할 계획·인계 기록 | 요청하지 않은 번역/코드 수정 |

- **배포용 빌드의 실제 컴파일·패키징을 할 수 없으면** 완성된 업로드용 ZIP이라고 주장하지 않는다. 소스만 만들 수 있는 환경이라면 그 한계를 명시한다.
- 전달하기 전 ZIP 목록을 검사하여 개발 노트, 조사 JSON, `extras` 등 **규격 외 자료가 섞이지 않았는지** 확인한다. README·라이선스 등 **필수 프로젝트 파일을 개발 중간 문서로 오인하여 삭제하지 않는다.**
- 사용자가 개발 중간 메시지·임시 파일 정리를 요구하면 **최종 전달물에서만 해당 파일을 제외하거나 실제로 삭제한 범위**를 구분한다. **실제 삭제한 파일이 있다면 경로·삭제 사유를 채팅에 명시**한다. 단순히 ZIP에 넣지 않은 파일은 삭제했다고 주장하지 않는다.
- 파일명·기존 지원 폴더·스크립트의 의미를 임의로 바꾸지 않는다. 반드시 달라져야 할 구조 변경은 사전에 근거와 영향을 알리고 사용자 승인을 받는다.

## 7. `docs`·`records`·`note` 관리와 업데이트 노트 — 번역 작업의 필수 마지막 단계

**사용자 요청 여부와 관계없이** 작업 종료 시 `docs`의 현행 지침 개정 필요 여부, `records`의 실제 작업 기록 갱신, `note`의 공개 문서 갱신 필요 여부를 서로 구분해 점검한다. **작업 결과를 `docs/`에 신규 문서로 작성하거나 기록을 덧붙이지 않는다.** **필요한 문서만 갱신하며**, 작업 중간 변경을 공개 노트에 자동으로 추가하지 않는다. `note/update.md`는 이전에 실제 공개한 버전과 이번 최종 공개본의 순수한 차이만 기록한다. 동일 버전 출시 전 번복·재수정·빌드 오류 수정은 개발 인계 기록에만 남긴다. `docs/번역작업안내서.md`의 **0-1절**을 반드시 따른다. 업데이트 노트를 쓸 때는 `배포_업데이트노트_작성지침.md`의 **사용자 승인 양식(제목·설치 및 업데이트·신규 번역 지원·기존 번역 개선만)**을 따른다. 별도 날짜/호환 버전 부제목, 이전 업데이트 이력, 추가 섹션은 붙이지 않는다. 실제 업로드할 빌드 ZIP에서 **버전·호환 SPT·덮어쓰기만으로 업데이트 가능한지·필수 선행 모드 URL·신규 지원과 기존 개선**을 검증한다.

- 일반 사용자는 **빌드된 파일을 설치**한다. 소스 수정 방법·빌드 로그·임시 개발 파일·훅 클래스명은 공개 업데이트 노트에서 제외한다.
- 사용자 개인 설치 경로를 적지 않는다. 확인되지 않은 폴더 삭제를 요구하지 않는다.
- 제외한 모드나 실제 배포되지 않은 기능은 변경 사항에 넣지 않는다. 설치에 필수적인 제약만 짧게 적는다.

**설치 안내의 예외:** 기존 세 단계 덮어쓰기 안내는 실제 신규 설치와 기존 설치 모의검사에서 성립하는 경우에만 확정한다. 과거 호환 프로필처럼 덮어쓰기로 지워지지 않는 잔존 파일이 있으면 정확한 경로·영향을 밝히고 승인된 최소 삭제 안내만 반영한다. 전체 번역 폴더 삭제를 기본값으로 안내하지 않는다. `배포_업데이트노트_작성지침.md` 3·5절을 따른다.

**소스 빌드의 참조 라이브러리:** CMD는 설치된 게임의 위치를 요구하거나 검색하지 않는다. 필요한 클라이언트·서버 참조 DLL은 프로젝트 내 `references/client`, `references/server`에 따로 제공되어야 한다(상세 목록은 `references/README.md`). 참조 DLL이 없을 때에는 컴파일 불가 사유와 부족한 파일을 출력하며, 게임 설치 경로를 요구하는 방식으로 우회하지 않는다. 이 개발용 DLL은 배포 ZIP에 넣지 않는다.

**새 세션 방지 규칙:** 작업 중 생성하는 날짜·차수·모드별 감사 보고서 및 버전 증거는 `docs/records/`로만 출력한다. `docs/` 최상위에 기록을 직접 추가하거나 지정된 하위 폴더 밖에 저장하면 문서 검사에서 실패해야 한다. `docs/records/`, `docs/reference-data/`, `docs/tools/`는 정상 보관 위치다. 기록 파일 이름과 내용 때문에 `docs`의 기술 지침을 변경하지 않는다.

**소스 덮어쓰기 빌드 주의:** 압축을 덮어써도 구버전 문서는 자동 삭제되지 않는다. 빌드 진입점은 문서를 자동 이동·삭제하지 않으며, 옛 문서나 GPT 지침 파일의 누락 때문에 빌드를 차단하지 않는다. 문서 분류와 링크 검사는 별도 `python docs/tools/verify_workflow.py documents`로 수행하고, 사용자에게 제공할 소스 정리 때 실제 이동·삭제 파일을 고지한다. 배포 ZIP에는 런타임 데이터만 포함하도록 별도 검증한다.

**폴더 분류:** `docs/`는 GPT 자료의 유일한 관리 루트이며 최상위에는 현행 지시·프롬프트·스키마·공통 양식만 둔다. 기술 감사 결과·작업별 인계·수정 기록·버전 증거는 `docs/records/`, 참고 자료는 `docs/reference-data/`, 검증 도구는 `docs/tools/`에 둔다. 프로젝트 루트 등에 GPT 작업 기록·도구 사본을 생성하지 않는다. `note/`에는 일반 사용자가 열람·게시할 `README.md`, `번역지원모드목록.md`, `update.md`를 둔다. 사용자 공개용 안내를 `docs/`에 중복 생성하지 않는다. `build/build_supported_mods.py`의 목록 출력 위치는 `note/`다. 배포 ZIP의 내부 설치 구조(`BepInEx`, `SPT_Runtime`)는 이 문서 분류 때문에 변경하지 않는다.

**문서별 갱신 트리거:** `docs/records`의 버전 관리 대장·근거 CSV 및 각 회차 수정 기록을 현재 경로에서 관리한다.  번역 대상 모드의 원본/공식 버전 확인·변경 → `mod_version`, `docs/records/versioning/번역_원본모드_버전관리대장_20261023.md`, `docs/records/versioning/번역_원본모드_버전_근거목록_20261023.csv`의 일치 및 미확인 사유 점검(실제 번역 검증과 분리); 번역 대상·지원 범위·`mod_version` 변경 → `build/build_supported_mods.py`로 `note/번역지원모드목록.md` 재생성 후 버전 표기·인계 기록 점검; 버전·필수 모드·설치 방식 변경 → `note/README.md` 점검; 번역 규칙·훅 정책·검증 방식 변경 → `docs/번역작업안내서.md`·관련 Prompt·기술 문서 갱신. `note/update.md`는 **지난 공개본 대비 최종 배포본의 변경점**이 확정되거나 기존 공개 초안이 부정확할 때만 수정하며, 동일 버전의 개발 단계별 수정 사항을 항목으로 누적하지 않는다. 신규 작업일지·개발 중간 메시지는 `note/`에 넣지 않는다. 마지막 전달 전에 문서와 실제 소스의 일치 여부를 확인한다.
